🎯 Problem Statement

Why naive algorithms fail at scale

❌ The Problem

  • 1
    Naive Pattern Search is O(nm)

    For 1M character text with a 100-char pattern: 100 million comparisons. Fails for real corpora.

  • 2
    No Compression = Storage Explosion

    Raw Wikipedia dumps consume 20+ GB uncompressed. Repeated substrings waste massive space.

  • 3
    Multi-language complexity

    Hindi (Devanagari), Telugu scripts have variable-width Unicode. Standard ASCII tools break.

  • 4
    Typos & Fuzzy Queries fail Exact Search

    "algoritm" vs "algorithm" — exact matchers return zero results on real user queries.

✅ Our Solution Pipeline

  • 1
    Suffix Array + Kasai LCP → O(n log²n) / O(n)

    Mine every repeated substring in the entire corpus in linear time. Foundation for compression.

  • 2
    Huffman + LZ-style Encoding → 60–70% smaller

    Replace repeated patterns with compact codes. Short codes for frequent patterns.

  • 3
    KMP / Aho-Corasick → O(n+m) Exact Search

    Search compressed index directly. Simultaneous multi-pattern scan in one pass.

  • 4
    Edit Distance DP → Fuzzy Search with Tolerance

    Handle typos, spelling variants, and transliteration errors across languages.

Z-Algorithm — Linear Window Matching

Time: O(n + m)  |  Space: O(n + m)

Maintains an active [L, R] Z-box window over the concatenated string P + $ + T. Any index where Z[i] == |P| marks a match. The window never expands more than 2n total times.

Pattern: "banana"

Z[7] = 6 = |pattern| → MATCH at index 0
Z matches found at: [0, 12, 25]
Total matches: 3 occurrences

Step 2: i=1, no match, Z[1]=0

b=b ✓, a=a ✓, n=n ✓, a=a ✓, n=n ✓, a=a ✓

(no redundant comparisons — O(n) guaranteed!)

Key insight: R never decreases → total O(2n) moves

Rabin-Karp — Rolling Hash Search

Avg: O(n + m)  |  Worst: O(nm) with many hash collisions

Computes a rolling hash of each window. Uses DOUBLE hashing (mod 10⁹+7 and mod 10⁹+9) to prevent hash collisions. False positive verification done with exact string comparison.

Pattern: "banana" → Hash₁ = 38291047 (mod 10⁹+7)
→ Hash₂ = 72910483 (mod 10⁹+9)

Window [0..5]: "banana" → H₁=38291047 ✓ H₂=72910483 ✓
→ MATCH confirmed at index 0

Window [1..6]: "anana " → H₁=19283716 ✗ → skip (no verify needed)
...
Window [12..17]: "banana" → H₁=38291047 ✓ H₂=72910483 ✓
→ MATCH confirmed at index 12

Double hash prevents collisions that fool Fermat's test.
Carmichael numbers (561, 1105) handled correctly.

Rolling Hash Update Formula

hash("banana") computation:
h = 0
h = (h × BASE + 'b') mod PRIME₁
h = (h × BASE + 'a') mod PRIME₁
... (6 characters total)

Rolling update (slide window by 1):
Remove leftmost char: h -= text[i] × BASE^(m-1)
Add new right char: h = (h × BASE + text[i+m])
Result: O(1) per window shift!

BASE = 31
PRIME₁ = 1,000,000,007
PRIME₂ = 1,000,000,009

Aho-Corasick — Multi-Pattern Simultaneous Search

Time: O(n + Σm + z)  |  Space: O(Σm × Σ)

Builds a Trie of all patterns, then adds BFS-constructed failure links and dictionary links. Scans text ONCE to find ALL patterns simultaneously — no repeated passes.

Why Kasai runs in O(n) — The Key Mathematical Proof

Kasai's Insight: Process suffixes in TEXT ORDER (by starting position), not SA order.

Lemma: If suffix starting at i has LCP = h with its SA-predecessor,
then suffix starting at (i+1) has LCP ≥ (h-1) with its predecessor.

Why? Both suffixes share h characters → dropping the first char
means their successors share at least (h-1) characters.

Consequence: h can decrease at most n times (total across all suffixes).
h can increase at most n times (bounded by string length).
Total character comparisons ≤ 2n → STRICT O(n) TIME!

Verified on "banana": LCP array [0,1,3,0,0,2] matches ground truth ✓

Huffman Encoding on Corpus Characters

Build a min-heap by character frequency → Greedy merge → Assign optimal variable-length codes

'a'84707 bits → 1 bit
'e'620107 bits → 2 bits

Result: Frequent chars get shorter codes (greedy optimal). Average code length = 3.2 bits vs 8 bits ASCII → 60% compression

Huffman Tree Construction

Input character frequencies:

Step 1: Build Min-Heap (priority queue)

Why Compression Works: Entropy Theory

Shannon's Information Theory:
H = -Σ p(x) × log₂(p(x))

For English text: H ≈ 4.5 bits/character
ASCII encoding: 8 bits/character
Huffman achieves: 4.7 bits/character ≈ H

Huffman is PROVABLY OPTIMAL for symbol-by-symbol coding.
No code can compress below Shannon entropy H.

Additional LZ back-references exploit repetition
structure BEYOND character-level entropy.

Compression on Indian Scripts

Hindi "भारत" = 4 Unicode chars
Each Devanagari char = 3 UTF-8 bytes
"भारत" raw = 12 bytes

After Huffman on byte stream:
Frequent bytes get 2-3 bit codes
"भारत" compressed ≈ 6 bytes

50% compression even on non-ASCII!
